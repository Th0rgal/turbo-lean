## Aborted attempts 1 and 2 (no measurements) and the memory limit

Attempt 1 (2026-10-31T22:04Z, `attempt1-aborted/`) and attempt 2 (2026-11-01T00:00Z, `attempt2-aborted/`) used identical flags with default parallelism (LEAN_NUM_THREADS unset, lake default = 8 jobs). Both died about 11-12 minutes in, while still in the **untimed** stock `lake build FV` prime, at modules 288/4556 and 375/4556. Attempt 1 logged `bench_clifv: interrupted`, i.e. it got a signal. Attempt 2 ran as a durable node job; the node later reported it `failed` with the whole process tree gone and no exit file. Neither run produced a pair.

Cause found (`diag-memory/`, diagnostics only, outside the experiment): this node runs every job in a systemd scope with `memory.max` = 16 GiB, `memory.high` about 14.4 GiB and swap 0 (`SANDBOXED_NODE_JOB_MEMORY_BYTES=17179869184`). Resuming the same stock prime with default parallelism (8 concurrent `lean` processes) hit the 14.4 GiB `memory.high` throttle within 2 minutes. `memory.events` showed `high` rising to more than 100k, and the build stalled at 14.7 GiB. The node agent binary contains the message "a child process also exceeded this job's memory budget". The node agent killing over-budget jobs is the most likely cause of both aborts; this is inferred, since the kernel/journal logs are not readable from here. clifv modules reach 1-6 GiB RSS each. With `LEAN_NUM_THREADS=4` (4 lean procs) the cgroup peak was still 14.6 GiB, i.e. at the throttle line.

**Attempt 3 (this report)** therefore exports `LEAN_NUM_THREADS=3 TURBO_LEAN_JOBS=3 TURBO_LEAN_MAX_MEMORY_MB=14336` for **both arms** (`logs/run3.sh`). The runner records LEAN_NUM_THREADS. Lake's module-job parallelism follows LEAN_NUM_THREADS (observed: 4 concurrent `lean` processes with LEAN_NUM_THREADS=4 vs 8 unset); turbo-lean's follows TURBO_LEAN_JOBS. These are not stock 8-thread numbers: they measure a 3-way-parallel build under a 16 GiB cap.
